# Скил: Безопасные миграции базы данных (database-migration)

## 1. Назначение и триггеры
- **Применять когда:** добавлена или изменена модель в каталоге моделей (таблица, колонка, индекс, внешний ключ).
- **НЕ применять:** когда схема БД не меняется.

## 2. Предусловия (Inputs)
- Защитный слепок `tests/characterization/` зелёный.
- СУБД запущена, текущая схема соответствует `uv run alembic current`.

## 3. Пошаговая процедура (Execution Steps)
### Фаза 1: Модель
1. Внести изменение в модель SQLAlchemy.
2. НЕ вызывать `Base.metadata.create_all()` в коде приложения: схемой управляет только Alembic.
3. Новая модель обязана быть импортирована в `alembic/env.py` — иначе автогенерация даст пустую ревизию.
### Фаза 2: Ревизия
1. Сгенерировать: `uv run alembic revision --autogenerate -m "<описание>"`.
2. Проверить файл вручную: явные имена индексов и внешних ключей, `server_default` для новых обязательных колонок, `ondelete` для внешних ключей.
3. Заполнить `downgrade()` полноценно: удалить индексы и таблицы в обратном порядке. Никаких пустых `pass`.
### Фаза 3: Маятник миграции
1. `uv run alembic upgrade head` — накатить.
2. `uv run alembic downgrade -1` — откат обязан пройти чисто (ловит пустой/неполный downgrade).
3. `uv run alembic upgrade head` — накатить повторно (ловит остатки после отката).
4. `uv run alembic check` — модели и схема БД синхронны.

## 4. Выходные артефакты (Outputs)
- Файл `alembic/versions/<id>_<slug>.py` с рабочими `upgrade()` и `downgrade()`.

## 5. Ворота готовности (Definition of Done)
1. Маятник `upgrade head -> downgrade -1 -> upgrade head` завершается кодом 0.
2. `uv run alembic check` возвращает 0.
3. `uv run pytest -q` возвращает 0.

## 6. Стоп-условия и откат
- Запрещено удалять/переименовывать существующие колонки без двухфазного плана Expand-and-Contract.
- Запрещено менять БД вручную через `psql`/DDL в обход ревизии.
- `downgrade -1` падает — остановиться, выполнить `git restore alembic/versions/`, удалить сгенерированные неотслеживаемые файлы ревизий и доложить человеку.
