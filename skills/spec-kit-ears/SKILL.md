# Скил: spec-kit-ears

## Триггеры
- Новый эндпоинт или сервис в монолите.
- Высокий риск конфликта бизнес-логики со смежными доменами.
- Нужна спецификация до написания тестов и кода.

## Процедура
1. Прочитать паспорт домена и бизнес-требование.
2. Классифицировать каждое требование по шаблонам: `Система ДОЛЖНА` (вездесущее); `КОГДА событие, система ДОЛЖНА` (по событию); `ПОКА состояние, система ДОЛЖНА` (по состоянию); `ЕСЛИ условие, система ДОЛЖНА` (опциональное); `ЕСЛИ сбой, ТО система ДОЛЖНА` (нежелательное поведение).
3. Записать требования строками `- [REQ-EARS-NN] ...` в `specs/<фича>-ears.md`.
4. Для сложных требований составить матрицу сценариев и указать уровень проверки.
5. Выполнить `python3 tools/ears_linter.py`: код возврата обязан быть 0.

## Ворота готовности
- [ ] Каждое требование укладывается в один из пяти шаблонов.
- [ ] Описаны негативные случаи: 402, 503, дубль `transaction_id`.
- [ ] Деньги типизированы целым числом копеек, без `float`.

## Стоп-условия
- Требование не ложится в шаблон: переформулировать с автором задачи.
- Противоречие с паспортом домена: приоритет у паспорта.
