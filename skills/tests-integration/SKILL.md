# Скил: Интеграционные тесты с реальной базой данных (tests-integration)

## 1. Назначение и триггеры
- **Применять когда:** нужно проверить слои в сборе: HTTP -> Service -> Repository -> БД.
- **НЕ применять:** для чистой бизнес-логики без БД — для неё есть скил `tests-unit`.

## 2. Предусловия (Inputs)
- Модульные тесты `tests/unit/` зелёные.
- БД проекта запущена, миграции накатаны (схему тестовой базы накатывает миграциями, не `create_all`).
- Тестовая БД отделена от базы разработки (имя с суффиксом `_test`).

## 3. Пошаговая процедура (Execution Steps)
### Фаза 1: Изоляция состояния
1. Проверить фикстуры `tests/conftest.py`: каждый тест живёт в транзакции с откатом — внешняя `connection.begin()`, сессия с `join_transaction_mode="create_savepoint"`, в `finally` — `session.close()` и `transaction.rollback()`.
2. Зависимость БД подменяется через `app.dependency_overrides` на тестовую сессию; после теста — `clear()`.
3. Защита от случайного запуска на боевой базе: проверка суффикса `_test` в имени БД (иначе `pytest.exit`).
### Фаза 2: Сквозные сценарии
1. Покрыть `tests/integration/test_api.py`: создание (201), чтение (200/307), несуществующий объект (404), невалидный ввод (422), конфликт уникальности, проверку состояния БД после операций.
2. Каждый сценарий проверяет три вещи: статус-код, JSON и состояние базы.
### Фаза 3: Проверка изоляции двойным прогоном
1. Выполнить `uv run pytest tests/integration/ -q && uv run pytest tests/integration/ -q`.
2. Оба прогона обязаны дать одинаковый зелёный результат без ручной очистки. Падение второго на уникальности — протечка состояния: чинить изоляцию, а не удалять тесты.
### Фаза 4: Правило «только вверх»
1. Поднять `fail_under` в `pyproject.toml` (например, 60 → 80). Снижать запрещено; сравнение значений — по `git diff pyproject.toml`.

## 4. Выходные артефакты (Outputs)
- `tests/integration/test_api.py` и обновлённая фикстура в `tests/conftest.py`.
- Поднятый `fail_under` в `pyproject.toml`.

## 5. Ворота готовности (Definition of Done)
1. Двойной запуск `uv run pytest tests/integration/ -q` проходит без ошибок уникальности и остаточных данных.
2. `uv run pytest -q --cov=app --cov-branch --cov-fail-under=<новый порог>` возвращает 0.
3. `uv run ruff check .` и `uv run basedpyright` возвращают 0.

## 6. Стоп-условия и откат
- Запрещено ходить в основную базу разработки и оставлять в ней данные тестов.
- Запрещено снижать `fail_under`.
- Второй прогон падает на уникальности — остановиться, исправить изоляцию (данные пишутся вне фикстуры), а не удалять тесты.
